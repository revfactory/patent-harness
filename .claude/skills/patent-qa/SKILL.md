# 출원 서류 형식·일관성 검사

formality-checker가 따르는 절차다. 형식 오류는 내용이 좋아도 보정 요구나 기재불비 거절로 이어지고, 보정은 범위를 줄이거나 시간을 쓴다. 기계로 찾을 수 있는 오류는 스크립트로 먼저 거르고, 사람의 판단이 필요한 오류에 정독 시간을 쓴다.

## 1. 스크립트 검사

```bash
python3 -I .claude/skills/patent-qa/scripts/check_claims.py _workspace/{case}/04_claim-drafter_claims_final.md
python3 -I .claude/skills/patent-qa/scripts/check_spec.py _workspace/{case}/05_spec-writer_specification.md \
  --claims _workspace/{case}/04_claim-drafter_claims_final.md --figures _workspace/{case}/05_drawing-designer_figures.md
```

- 출력 원문을 `_workspace/{case}/06_formality-checker_raw.txt`에 저장한다.
- `--json`을 붙이면 구조화된 결과를 받는다.
- 청구항은 `【청구항 N】` 형식이어야 읽힌다. 다른 형식이면 검사 보고서에 형식 불일치를 적고 정독으로만 검사한다.

| 스크립트 | 검사 | 오탐이 나는 경우 |
| --- | --- | --- |
| check_claims.py | 번호 누락·중복, 존재하지 않는 항 인용, 뒤 번호 인용, 다중→다중 종속, '및'으로 두 항 인용, 선행 근거, 불명확 표현, 문장 수, 도면 부호 괄호, 수치 목록 | 선행 근거: 용어를 다른 조사·어순으로 처음 쓴 경우. 불명확 표현: "등록", "정도"가 고유명사 일부인 경우 |
| check_spec.py | 필수 항목, 문단 번호, 부호 이름 충돌, 부호의 설명 누락, 도면 언급 불일치, 청구항 용어 뒷받침, 미완성 표시 | 뒷받침: 명세서에 띄어쓰기만 다르게 쓴 경우 |

## 2. 정독 검사

스크립트가 못 잡는 항목을 확인한다.

1. **청구항-명세서 대응표**: 청구항의 구성 요소마다 명세서에서 그 구성을 설명한 문단 번호와 도면 번호를 적는다. 빈칸이 있으면 뒷받침 요건 위험이다.
2. **수치 한정**: 청구항의 수치마다 명세서에 측정 방법이 정의됐는지, 실시예가 범위 안팎에 있는지 확인한다.
3. **용어 일관성**: 같은 대상을 다른 이름으로 부르는지(예: "돌기"와 "러그"), 다른 대상을 같은 이름으로 부르는지 확인한다.
4. **효과 근거**: 발명의 효과 절의 효과마다 그것을 내는 구성과 데이터(또는 미완성 표시)가 있는지 확인한다.
5. **선행문헌 인용**: 배경기술과 선행기술문헌 절의 번호가 검증 원장에 있는지, 번호 형식이 맞는지 확인한다.
6. **범주**: 물건 청구항에 방법 단계만 있거나, 방법 청구항에 구조만 있는지 확인한다.

## 3. 심각도

| 심각도 | 기준 | 예 |
| --- | --- | --- |
| 출원 불가 | 서류가 접수되지 않거나 반드시 보정 명령을 받는 오류 | 필수 항목 누락, 존재하지 않는 항 인용 |
| 보정 사유 | 기재불비 거절 이유가 될 수 있는 오류 | 선행 근거 없음, 측정법 없는 수치, 뒷받침 없음 |
| 권고 | 거절 사유는 아니나 고치면 좋은 것 | 문단 번호 건너뜀, 쓰이지 않는 부호 |
| 확인 | 사람이 확인할 목록 | 수치 목록, 미완성 표시 |

## 4. 보고서 형식

```
# 형식·일관성 검사 보고서
> 대상 파일과 버전, 검사일
## 요약 (심각도별 건수)
## 오류 목록
| 번호 | 심각도 | 위치 | 규칙 | 내용 | 고칠 방법 | 출처(스크립트/정독) |
## 걸러 낸 오탐
| 스크립트 지적 | 오탐 이유 |
## 청구항-명세서-도면 대응표
| 청구항 | 구성 | 명세서 문단 | 도면 | 상태 |
## 이전 검사 대비 (재검사 시)
```

재검사에서는 이전 오류마다 `해결`, `미해결`, `새 오류`를 표시한다.
