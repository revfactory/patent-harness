# 특허 발굴·출원 오케스트레이터

메인 세션이 리더가 되어 아래 단계를 실행한다. 각 단계 위에 실행 모드를 적었다. 이 스킬을 사용자가 불러오거나 이 하네스로 특허 과제를 처리해 달라고 요청하면 Workflow 사용에 동의한 것으로 본다. 워크플로 하나에 띄우는 에이전트는 기본 10명 미만으로 두고, 사용자가 "철저히", "전수"를 요청할 때만 늘린다.

## 실행 모드: 혼합

| 단계 | 실행 모드 | 선택 이유 |
| --- | --- | --- |
| 0 기존 작업 확인 | 메인 직접 | 파일 존재 확인만 필요하다 |
| 1 입력 준비 | 메인 직접 + 스크립트 | 번호 추출·텍스트 변환은 결과가 항상 같아야 한다 |
| 2 검증·보충 조사 | 워크플로 조율 | 문헌 목록을 미리 확정해 묶음별로 나누고, 판정을 스키마로 받아 코드로 합칠 수 있다 |
| 3 분석 | 서브에이전트 병렬 | 특허성·자유실시·공백 분석은 서로 독립이고 결과만 받으면 된다 |
| 4 발명 정리·시험 설계 | 서브에이전트 병렬 | 3단계 결론을 받아 각자 한 번 작성한다 |
| 5 청구항·모의 심사 | 지속형 에이전트 협업 | 작성자가 지적받은 항만 고치려면 이전 버전 맥락을 기억해야 한다 |
| 6 도면·명세서 | 지속형 에이전트 협업 | 부호표와 명세서가 서로 맞춰져야 하고 형식 검사 뒤 부분 수정이 이어진다 |
| 7 형식 검사 | 서브에이전트 → 지속형 수정 | 검사는 한 번, 수정은 5·6단계 에이전트에게 메시지로 맡긴다 |
| 8 출원 전략 | 서브에이전트 | 4단계 뒤 독립 실행 가능 |
| 9 보고서 | 서브에이전트 + 메인 최종 검토 | 편집은 한 번, 최종 판단은 리더가 한다 |

## 과제 유형

| 유형 | 입력 | 실행 단계 | 산출물 |
| --- | --- | --- | --- |
| R 보고서 검토·정리 | 기존 조사 보고서 | 0 → 1R → 2 → 3 → 4 → 5 → 6 → 7 → 8 → 9 | 검토 보고서, 발명신고서, 청구항, 명세서 초안, 시험 계획, 출원 일정 |
| D 신규 발굴 | 아이디어 메모, 기술 문서 | 0 → 1D → 2(검색 워크플로) → 3 → 후보 선택(사용자 확인) → 4 → 9 | 발굴 결과 보고서, 발명신고서 |
| F 출원 준비 | 확정된 후보(발명신고서) | 0 → 4 → 5 → 6 → 7 → 8 → 9 | 출원 준비 패키지 |

- R에서 사용자가 "검토만", "정리만"이라고 범위를 줄이면 6·7단계(명세서·도면)를 건너뛰고 보고서에 다음 단계로 적는다.
- D에서 후보를 고른 뒤 사용자가 원하면 F를 이어서 실행한다. 후보 선택은 사업 판단이 섞이므로 사용자에게 확인받는다.

모델은 각 정의 파일의 `model:`을 따른다. 모델 선택 이유는 정의 파일 주석에 있다. 메인 세션은 조율과 최종 판단을 맡는다.

### 에이전트 유형이 등록되지 않았을 때

`.claude/agents/`의 정의 파일은 세션이 시작될 때 등록된다. 하네스를 만든 세션이나 정의 파일을 고친 직후에는 `subagent_type`·`agentType`에 이 이름을 쓰면 "agent type not found"로 실패한다. 이때는 다음처럼 대체한다.

- Agent 도구: `subagent_type: "general-purpose"`, `model:` 정의 파일의 값, 프롬프트 첫 줄 "먼저 `.claude/agents/{name}.md`를 Read로 읽고 그 역할과 작업 원칙을 따른다." 지속형 에이전트는 `name`을 그대로 붙인다.
- Workflow: `args.fallback: true`를 넘긴다. 스크립트의 `run()`이 같은 방식으로 대체한다.
- 다음 세션부터는 대체 없이 정의 파일 이름을 쓴다. 같은 세션 안에서도 나중에 등록되는 경우가 있으므로, 시스템이 알려 주는 사용 가능 에이전트 목록에 이름이 보이면 그때부터 정의 파일 이름을 쓴다.

## 사건 폴더

사건마다 `{case}`(영문 소문자와 하이픈, 예: `shoe-sole`)를 정하고 아래 구조로 쓴다. `/tmp`와 세션 스크래치패드를 쓰지 않는다. 사용자 홈 폴더(`~/.claude/`, `~/.ccm/`의 메모리 디렉터리 포함)에도 쓰지 않는다. 하네스가 홈 폴더에 남기는 워크플로 결과·도구 출력은 `01_raw/` 등 사건 폴더로 복사해 쓴다. 에이전트를 띄울 때 프롬프트에 이 규칙을 넣고, 에이전트가 홈 폴더에 파일을 남겼으면 내용을 확인해 필요한 것은 프로젝트로 옮기고 원래 파일은 지운다.

```
_workspace/{case}/
├── 00_input/            원자료, source.txt, patent_refs.json, claims_ledger.md, link_map.md
├── 01_raw/              스크립트가 받은 원문 JSON
├── 01_verified_ledger.md   검증 원장(2단계 결과를 메인이 정리)
├── 01_supplement.md        보충 검색·시장 확인 결과
├── 02_*                 분석
├── 03_*                 발명신고서, 시험 계획
├── 04_*                 청구항 버전, 모의 심사
├── 05_*                 도면, 명세서
├── 06_*                 형식 검사
├── 07_*                 출원 전략
├── 08_*                 보고서 초안
├── freeze_{phase}.sha   단계 경계 동결 해시
└── run_meta.json        워크플로 runId, 기준일, 과제 유형
outputs/{case}/          사용자에게 넘길 최종본
```

## 0단계: 기존 작업 확인

**실행 모드:** 메인 직접

1. `_workspace/{case}/`가 없으면 처음부터 실행한다.
2. 있고 일부만 고쳐 달라는 요청이면 해당 단계만 다시 실행한다. 예: "청구항만 다시" → 5단계부터, "새 문헌 반영" → 2단계 보충 검색만 실행한 뒤 영향받는 3단계 분석과 5단계를 다시 실행한다.
3. 있고 새 입력(다른 보고서, 새 아이디어)이면 기존 폴더를 `_workspace/{case}_{YYYYMMDD-HHMM}/`로 옮기고 새로 실행한다.
4. 2단계를 다시 실행하는데 `run_meta.json`에 `runId`가 있으면 바뀐 부분만 고친 스크립트를 `resumeFromRunId`로 재개한다. 바뀌지 않은 `agent()` 호출은 캐시 결과를 쓴다.
5. 다시 호출하는 에이전트에게는 이전 산출물 경로와 바꿀 범위를 프롬프트에 넣는다.

## 1단계: 입력 준비

**실행 모드:** 메인 직접 + 스크립트

### 1R. 보고서 검토(R)

```bash
mkdir -p _workspace/{case}/00_input _workspace/{case}/01_raw
python3 -I .claude/skills/prior-art-search/scripts/extract_patent_refs.py {보고서.pdf} \
  --out _workspace/{case}/00_input/patent_refs.json --text-out _workspace/{case}/00_input/source_pypdf.txt
pdftotext -layout {보고서.pdf} _workspace/{case}/00_input/source.txt
```

그다음 메인이 직접 다음 파일을 만든다.

1. `00_input/link_map.md`: 화면 번호와 링크 대상 번호가 다른 쌍(공개번호↔등록번호). PDF는 링크 주석을 따로 확인한다.
2. `00_input/claims_ledger.md`: 원 보고서의 주장을 유형별로 나눈 목록.
   - P(문헌 서지·내용 주장): 번호 목록. 원 보고서의 절(기술 유형)별로 묶는다.
   - U(원 보고서가 "미열람"으로 남긴 문헌과 확인 과제)
   - M(시장·상용화 주장): 보도자료, 제품, 리뷰, 수치
   - L(법·제도 주장): 공지예외, 실용신안 제도, 거절 사유 추정 등. 3·8단계 에이전트가 확인한다
   - T(기술 주장): 원리, 시험 수치
   - J(판단): 후보별 신규성·진보성 등급, 권장안. 3단계에서 재평가한다
3. 2단계 `args` 초안: 문헌 묶음(묶음당 10~20건, 같은 기술 유형끼리), 보충 검색 과제, 시장 주장 목록.

### 1D. 신규 발굴(D)

`invention-miner`를 서브에이전트로 한 번 호출해 `03_invention-miner_disclosure.md` 초안을 만들고, 그 끝의 키워드·분류 후보로 2단계 검색 기준을 정한다.

## 2단계: 검증·보충 조사

**실행 모드:** 워크플로 조율

- R: `references/workflow-scripts.md`의 **A. patent-verify** 스크립트를 쓴다. 묶음 대조(citation-verifier) → 불일치 재확인(citation-verifier 1명) → 미열람 문헌·보충 검색(prior-art-searcher)·시장 확인(market-analyst)을 함께 돌린다.
- D: 같은 파일의 **B. patent-search** 스크립트를 쓴다. 검색 기준별 검색 → 중복 제거 → 누락 점검 → 추가 검색.
- 호출 뒤 완료 알림을 기다린다. 알림 전에 결과를 단정하지 않는다. 기다리는 동안 1단계 파일 정리나 3단계 프롬프트 준비를 한다.
- 결과를 받으면 메인이 다음을 쓴다.
  - `01_verified_ledger.md`: 번호 | 국가 | 출원인 | 우선일·출원일 | 상태(표시값) | 존속 판단 | 원 보고서 기재와의 차이 | 판정(1차/재확인) | URL. 1차와 재확인 판정이 엇갈리면 둘 다 적는다.
  - `01_supplement.md`: 미열람 문헌 확인 결과, 새로 찾은 문헌(X/Y/A), 시장 주장 판정.
  - `run_meta.json`: runId, 기준일, 과제 유형.
- 검증가는 Google 표시값만 보고 `불명`·`확인 불가`로 남기는 경우가 많다. 보충 과제가 J-PlatPat 경과정보 등으로 같은 문헌의 상태를 확인했으면 원장에 두 결과를 나란히 적고 어느 쪽을 채택했는지 밝힌다. 보충 과제끼리 같은 문헌을 다르게 판정했으면 원문을 직접 연 쪽을 채택하고 이유를 적는다.
- 반환값이 커서(수십만 자) 알림에 다 담기지 않는다. 알림의 출력 파일을 `01_raw/workflow_result.json`으로 복사한 뒤 스크립트로 표를 만든다.
- 보충 결과에 판단을 바꿀 수 있는데 열지 못한 문헌이 남으면 우선순위를 정해 prior-art-searcher 재조회를 3단계 분석과 같은 메시지에서 띄운다. 결과(`01_supplement_r2.md`)가 오면 결론이 바뀌는 3단계 분석가에게만 `SendMessage`로 넘겨 해당 부분을 고치게 한다. 3단계를 재조회 뒤로 미루지 않는 이유는 재조회가 Google 차단 해제를 기다려야 해 길어질 수 있기 때문이다.

## 3단계: 분석

**실행 모드:** 서브에이전트 병렬(한 메시지에서 세 번 호출, `name` 없이 단발 실행)

| subagent_type | 입력 | 지시 핵심 |
| --- | --- | --- |
| patentability-analyst | 원 보고서 후보 설명(source.txt 해당 절), 원장, 보충 결과 | 후보별 재평가. 원 판단 → 수정 판단 → 근거. 원 보고서 청구항 1 초안의 신규성·진보성. L·T 주장 가운데 특허성에 관한 것 확인 |
| fto-analyst | 원장, 후보 실시 형태 | 존속 권리 대비, 국가별 위험, 자유 실시 기술 목록 검증 |
| whitespace-strategist | 원장, 보충 결과, 원 보고서 분포표 | 분포·공백 판단 재검토, 후보 보강·추가 후보 |

세 결과를 받으면 메인이 권장 후보를 정한다. 결과끼리 결론이 다르면 근거를 비교해 정하고 `02_lead_decision.md`에 이유를 남긴다. R에서 원 보고서 권장안과 다른 후보를 고르면 이 파일에 원 권장안과 비교한 이유를 적는다.

## 4단계: 발명 정리·시험 설계

**실행 모드:** 서브에이전트 병렬(두 번 호출, 단발)

- invention-miner: 권장 후보의 발명신고서와 발명자 질문. 입력은 `02_lead_decision.md`, 3단계 산출물, 원자료. R 과제에서는 `model: "opus"`로 낮춰 호출한다(정리 범위가 정해져 있으므로).
- experiment-designer: 권장 후보의 진보성 주장별 시험 계획.

## 5단계: 청구항 작성·모의 심사

**실행 모드:** 지속형 에이전트 협업

1. 한 메시지에서 두 에이전트를 띄운다.
   - `Agent(name: "claim-drafter", subagent_type: "claim-drafter", prompt: "역할·입력 파일·출력 경로·첫 보고에 쓸 수 있는 도구 목록")`
   - `Agent(name: "examiner-simulator", subagent_type: "examiner-simulator", prompt: "대기. 리더가 검토 대상 파일을 보내면 시작")`
2. claim-drafter가 `04_claim-drafter_claims_v1.md`를 쓰면, 메인이 `check_claims.py`를 먼저 돌려 형식 오류를 claim-drafter에게 돌려보낸다(모듈 완성 즉시 검사). 형식 오류가 없으면 examiner-simulator에게 `SendMessage`로 v1 검토를 맡긴다.
3. 모의 의견서 `04_examiner-simulator_oa_v1.md`를 받으면 claim-drafter에게 보내 `v2`와 대응표를 만들게 한다. examiner-simulator에게 v2 재검토를 맡긴다.
4. 넘겨준 파일은 받은 쪽이 읽는 동안 고치지 않는다. 의견서나 청구항을 넘긴 뒤 보완할 일이 생기면 작성자는 새 파일을 쓰지 않고 리더에게 먼저 알리고, 리더가 받는 쪽에 보완 사실과 바뀐 점을 다시 보낸다. 실제 사건에서 의견서 보완본과 청구항 v2 작성이 엇갈려 거절 이유 하나가 대응표에서 빠졌다.
5. 반복은 최대 2회다. 2회 뒤에도 미해소 거절 이유가 남으면 남은 위험으로 보고서에 적는다. 끝없이 고치면 범위만 좁아지기 때문이다.
6. 마지막 버전을 `04_claim-drafter_claims_final.md`로 복사하고 동결한다(아래 동결 절차).

## 6단계: 도면·명세서

**실행 모드:** 지속형 에이전트 협업

1. `Agent(name: "drawing-designer", subagent_type: "drawing-designer", ...)`로 도면 목록·부호표·SVG를 만든다.
2. 부호표가 나오면 `Agent(name: "spec-writer", subagent_type: "spec-writer", ...)`에게 명세서를 맡긴다. 입력: 청구항 확정본, 발명신고서, 부호표, 시험 계획, 원장.
3. spec-writer가 도면 추가를 요청하면 메인이 drawing-designer에게 전달한다. 청구항 용어 변경 요청은 claim-drafter에게 전달하되, 동결 뒤이므로 새 버전 파일로 쓰게 한다.

## 7단계: 형식 검사

**실행 모드:** 서브에이전트(검사) → 지속형(수정)

1. formality-checker를 단발로 호출해 `06_formality-checker_report.md`를 받는다.
2. `출원 불가`·`보정 사유` 항목을 해당 작성자(claim-drafter, spec-writer, drawing-designer)에게 `SendMessage`로 전달한다. 작성자는 이전 맥락을 유지하므로 지적 항목만 고친다.
3. formality-checker를 한 번 더 호출해 재검사한다. 재검사는 1회로 끝내고 남은 항목은 보고서에 적는다.

## 8단계: 출원 전략

**실행 모드:** 서브에이전트(단발). 4단계가 끝나면 5~7단계와 겹쳐 실행해도 된다.

filing-strategist 입력: 3단계 분석, 시험 계획, `02_lead_decision.md`, 원장의 L 주장 목록. 기준일은 오늘 날짜를 넘긴다.

## 9단계: 보고서와 최종본

**실행 모드:** 서브에이전트(단발) + 메인 검토

1. report-editor에게 `_workspace/{case}/` 산출물 목록과 보고서 종류(patent-report 스킬 1절)를 넘긴다.
2. 메인이 초안을 읽고 확인한다: 결론이 산출물과 일치하는가, 근거 없는 문장이 없는가, Markdown 표가 깨지지 않는가.
3. 최종본을 `outputs/{case}/`에 복사한다. 기본 구성:
   - `01_검토보고서.md` (또는 발굴 결과 보고서)
   - `02_발명신고서.md`, `03_청구범위.md`, `04_명세서_초안.md`, `05_도면/`, `06_시험계획.md`, `07_출원전략_일정.md`, `08_검증원장.md`
4. 사용자에게 결론, 바뀐 판단, 남은 확인 사항, 파일 위치를 보고한다.

## 동결 절차(지속형 단계 경계)

이름 있는 에이전트는 완료 뒤에도 메시지를 받아 파일을 고칠 수 있다. 다음 단계가 읽을 파일이 바뀌지 않게 단계를 넘길 때 동결한다.

1. 해당 단계 에이전트가 모두 완료를 보고했는지 확인한다.
2. `SendMessage`로 동결을 알린다: "이후 고칠 내용은 기존 파일을 고치지 말고 `_v{다음}` 새 파일로 쓰고 리더에게 알려라."
3. `shasum _workspace/{case}/04_* > _workspace/{case}/freeze_04.sha`
4. 9단계 직전에 `shasum -c`로 바뀌지 않았는지 확인한다. 바뀌었으면 무엇이 바뀌었는지 보고 영향받는 단계를 다시 실행할지 정한다.

## 오류 처리

| Google Patents 접속 실패가 반복 | 다시 시도하지 않는다. 처리한 번호까지만 원장에 쓰고 나머지를 `확인 불가(네트워크)`로 남긴 뒤 사용자에게 알린다 |
| KIPRIS·J-PlatPat 접근 차단 | 대체 데이터베이스 결과를 쓰고 "원부 확인 필요" 목록에 올린다 |
| 서브에이전트 실패 | 한 번 다시 호출한다. 다시 실패하면 해당 산출물 없이 진행하고 보고서에 누락을 적는다 |
| 지속형 에이전트 무응답 | `SendMessage`로 상태를 묻고 다시 지시한다. 그래도 안 되면 같은 유형을 새 이름(예: `claim-drafter-b`)으로 띄우고 이전 버전 파일 경로를 넘긴다 |
| 사용량 한도·인증 만료·권한 거부 | 다시 시도하지 않는다. 부분 산출물을 열어 어디까지 됐는지 확인하고(파일 끝에 `</content>` 같은 도구 호출 문자열이 섞였는지, 마지막 표 행이 잘렸는지도 본다) `_workspace/{case}/incomplete.md`에 기록한 뒤 사용자에게 알린다. 한도라면 풀리는 시각도 알린다 |
| 산출물끼리 결론 충돌 | 지우지 않고 출처와 함께 나란히 적는다. 메인이 고른 쪽과 이유를 `02_lead_decision.md`에 남긴다 |
| 에이전트가 멈춘 자리를 메인이 채울 때 | 직접 확인한 사실만 반영한다. 에이전트의 판단(어떤 문헌을 왜 뺐는지)은 추측해 채우지 않는다 |
| 정의 파일의 `tools`가 실행 시 빠짐 | 첫 보고의 도구 목록으로 확인한다. 빠진 도구가 필요한 일은 메인이 대신하거나 정의 파일의 제한을 푼다 |
| "agent type not found" | 정의 파일이 이 세션에 등록되지 않은 것이다. 「에이전트 유형이 등록되지 않았을 때」 절에 따라 general-purpose로 대체 실행한다. 다시 시도하지 않는다 |

- 외부로 내용을 보내는 일(공유 문서 게시, 외부 서비스 업로드). 출원 전 공개가 되기 때문이다

## 테스트 시나리오

### 정상 흐름(R)
1. 사용자가 "이 조사 보고서 검토하고 정리해줘"와 PDF를 준다.
2. 1R에서 번호 69건을 뽑고, 공개↔등록 쌍을 link_map에 정리하고, 묶음 5개와 보충 과제 2개, 시장 주장 목록을 만든다.
3. 2단계 워크플로가 대조 5명 + 재확인 1명 + 보충 3명으로 끝나고, 메인이 원장과 보충 파일을 쓴다.
4. 3·4단계 산출물이 생기고, 5단계에서 모의 심사를 2회 이내로 주고받아 청구항 확정본을 동결한다.
5. 6·7단계를 거쳐 명세서 초안과 형식 검사 보고서가 생기고, 8·9단계 뒤 `outputs/{case}/`에 최종본이 놓인다.

### 오류 흐름
1. 2단계에서 묶음 3이 네트워크 오류로 `null`을 반환한다.
2. 스크립트 로그에 "대조 실패 묶음 1개: B3"이 나온다. 메인은 묶음 3만 다시 실행하도록 `resumeFromRunId`로 재개한다.
3. 재실패하면 묶음 3의 번호를 원장에 `검증 실패`로 적고, 보고서 "검토 범위" 절에 미검증 건수를 밝힌다.

### 오류 흐름(지속형)
1. 5단계에서 examiner-simulator가 응답하지 않는다.
2. `SendMessage`로 상태를 묻고 다시 지시한다. 그래도 응답이 없으면 `examiner-simulator-b`를 새로 띄워 `04_claim-drafter_claims_v{n}.md`와 원장 경로를 넘긴다.
3. 보고서 모의 심사 절에 "대체 에이전트로 재검토"라고 적는다.
