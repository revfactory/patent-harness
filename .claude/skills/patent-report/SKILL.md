# 특허 보고서 편집

report-editor가 따르는 절차다. 보고서는 읽는 사람이 결론과 할 일을 첫 쪽에서 알 수 있어야 하고, 모든 주장이 근거 파일까지 추적돼야 한다.

## 1. 보고서 종류

| 종류 | 언제 | 구조 |
| --- | --- | --- |
| 검토 보고서 | 기존 조사 보고서를 검토한 과제 | `references/report-templates.md` 1절 |
| 발굴 결과 보고서 | 새 아이디어에서 후보를 도출한 과제 | 2절 |
| 출원 준비 패키지 안내 | 청구항·명세서 초안까지 만든 과제 | 3절 |

과제가 여러 종류에 걸치면 검토 보고서를 본문으로 하고 나머지를 부록으로 붙인다.

## 2. 편집 원칙

- **결론 먼저**: 첫 절에 결론 3~6개, 권장 조치, 가장 가까운 기한을 둔다.
- **근거 표시**: 판정·수치마다 근거(문헌 번호, `_workspace` 파일명, 외부 출처 URL)를 붙인다. 근거가 없는 문장은 보고서에 넣지 않고 리더에게 알린다.
- **바뀐 것 구분**: 기존 보고서를 검토했으면 "확인됨 / 바로잡음 / 새로 추가 / 확인 불가"를 표로 나눈다. 검토 과제의 핵심 산출물은 "무엇이 바뀌었는가"다.
- **충돌 보존**: 산출물끼리 결론이 다르면 지우지 말고 두 결론과 근거를 나란히 적고, 어느 쪽을 따를지 판단할 사람(변리사, 발명자)을 적는다.
- **불확실성 표시**: Google Patents 법적 상태처럼 추정값은 추정이라고 적는다. 법률 자문이 아니라는 문장을 첫머리에 둔다.
- **분량**: 본문은 결정에 필요한 내용만 둔다. 문헌 전체 목록, 대비표 전체, 검색 이력은 부록이나 `_workspace` 파일 링크로 보낸다.

## 3. 문장 규칙

- 한국어 화자가 처음부터 한국어로 쓴 문장으로 쓴다. "~에 있어서"(청구항 인용 제외), "~를 가지고 있다", "~에 대해", "~를 통해"를 습관적으로 쓰지 않는다.
- 비유 표현(은유, 직유, 의인화, 관용적 비유)을 쓰지 않는다. 대상을 직접 가리키는 말과 실제 수치·사례로 쓴다. 예: "특허 지형" 대신 "기술 유형별 선행문헌 분포".
- 한 문장에 한 가지 내용을 쓴다. 문장 끝은 "~다"로 통일한다.
- 전문 용어는 처음 나올 때 한 번 풀어 쓴다. 예: 자유실시(FTO, 남의 특허를 침해하지 않고 제품을 실시할 수 있는지에 대한 판단).

## 4. Markdown 규칙

- 제목, 표, 목록 앞뒤에 빈 줄을 둔다.
- 표의 열 수를 모든 행에서 맞춘다.
- 강조(`**`)와 코드(`` ` ``)는 여는 기호와 닫는 기호를 짝지어 쓴다.
- Markdown 기호로 읽힐 수 있는 문자(`*`, `_`, `|`, `#`)를 일반 문자로 쓸 때는 앞에 `\`를 붙인다.

## 5. 최종 점검

보고서를 넘기기 전에 다음을 확인한다.

1. 첫 절만 읽어도 결론, 권장 조치, 기한을 알 수 있는가
2. 모든 판정에 근거가 붙었는가
3. 기존 보고서와 다른 판단은 모두 "기존 → 수정 → 근거"로 적었는가
4. 남은 확인 사항에 담당자(발명자, 변리사, 시험기관)가 적혔는가
5. Markdown 표가 깨지지 않는가
